DCIMe · Version 2.1 · Groundwork

What is broken, and the order to fix it

A full audit of the data path — from what a technician types on a phone, through the database, to the cell it lands in inside the two Excel workbooks — followed by a staged plan to unify the model, correct the mapping, and build the detailed analytics layer.

Scope · data input → interpretation → Excel Codebase · 32,346 lines TS/TSX Site · SITE_01, 47 assets, 14 rooms Status · stages 1–5 complete · awaiting operating limits
01

The short version

The system is not fractured because anyone built it badly. It is fractured because the same facts — what equipment exists, what it measures, where that reading goes — were written down three separate times, in three different places, and those three copies have drifted apart. Every symptom below traces back to that one cause.

The most serious consequence is not architectural, it is factual: the commercial logbook currently writes every room's temperature under the wrong room's heading. That is a signed compliance record going out with mis-attributed data. It is fixable in an afternoon, but it should be fixed knowing why it happened, or it will happen again.

02

How data actually moves today

Worth stating plainly, because the shape of the problem is visible in the shape of the diagram. There is one authoritative path and two shadow copies alongside it.

The registry feeds nothing. It holds one row in production — a stray oil_pressure on TPL_GENSET_1MW — so get_site_form_definition() returns zero equipment groups and the shift form has been driven by the blueprint JSON the whole time. The registry was built, wired up and never loaded. The blueprint JSON feeds seven runtime modules. The TypeScript mapping file feeds the Excel writer alone — even though equipment_parameters already carries excel_workbook, excel_sheet_name and excel_column_index columns built for exactly that purpose. Those columns are populated by one function, in seedDatabase.ts, which nothing imports.

03

Findings

Ordered by consequence. Everything here was verified against the actual template files and the actual code, not inferred.

Data integrity

Every room's temperature is written under the wrong room in the commercial logbook

The Temp Record sheet has seven room pairs. The mapping expects nine, because it leads with two rooms that do not exist anywhere in the blueprint — zesco_lt and rmu_ht. Those four phantom columns push every real room four columns to the right.

HQ Power Room's reading lands under Data Room. Server Room's lands under Power Room 1. IT Room 1's temperature lands in the Average of all rooms column and its humidity in Remarks & Sign. IT Room 2 is written past the end of the table entirely. Columns C–F stay blank.

Data loss

The PAC sheet overwrites itself every day and drifts a row every two hours

The aircon sheet holds 8,543 rows — 31 days × 12 two-hourly rounds × 23 units. The row formula is 5 + floor(hour/2)*24 + index. It has three faults at once: there is no day term, so all 31 days write over the same block; the stride is 24 where the template's block is 23, so each round drifts one row further out; and the base is 5 where data starts at row 6.

In practice roughly 292 of 8,543 rows are ever touched, and the month's aircon record is the last day only. The correct expression is 6 + ((day−1)*12 + floor(hour/2)) * 23 + index.

Evidence · excelExportEngine.ts:230. Template block confirmed: R6–R28 is 23 units, R29 begins the next round. getPacEquipmentIndex returns 0-based indices.

Data integrity

Generator logs are written one row too high

On every DG sheet the header occupies rows 2–3 and day 1 belongs in row 4. The formula is 2 + day, which puts day 1 into row 3 — the sub-header — and shifts the whole month up by one day. Should be 3 + day.

The neighbouring Fuel Record formula (5 + day) is correct, which is how the error survived: the two sheets sit side by side and only one of them is wrong.

Evidence · excelExportEngine.ts:222. Confirmed identical layout on DG-1, DG-3 and DG-HQ (A4 = day 1).

Silent

Half the workbook is derived by formula, and nothing tells Excel to recalculate

Room Temp · Auto Update, Summary · Temp & Hum, PUE Trend, and the four Power Plant check sheets contain no data of their own — they are formulas reading the day sheets. The writer correctly refuses to overwrite formula cells, but never sets fullCalcOnLoad, so the file ships carrying the template's cached results.

Whether the recipient sees real numbers depends on their Excel's recalculation settings. That is not a property a compliance record should have.

Evidence · no calcProperties anywhere in excelExportEngine.ts; formula guard at line 240.

Drift

291 of 614 mappings point at metrics nobody captures

Of 324 metrics defined in the blueprint, 323 have an Excel destination — coverage is genuinely good. The problem runs the other way: 291 mapping keys have no source. Chiefly the per-unit electrical columns on the PAC sheet — voltage RY/YB/BR, current R/Y/B/N, daily abnormality — for all 27 aircons, plus the two phantom rooms above.

So the aircon sheet's electrical half is structurally blank, and nothing reports that. Each one is a decision waiting to be made: either the technician should be capturing it, or the column should go.

Evidence · set difference between blueprint metric ids and EXCEL_MAPPINGS.SITE_01 keys. Only unmapped metric: dg_hq_charged_status.

Correctness

The app's PUE and the workbook's PUE are different numbers

The workbook defines IT load as rectifier DC power plus UPS output: (rect1_V×A + rect2_V×A)/1000 + UPS kW. The application uses UPS output alone. Dropping the rectifiers from the denominator inflates PUE — and the two figures will be quoted side by side in the same meeting.

Same neighbourhood: DG_BURN_RATE_LPH = 150 is a hard-coded fleet estimate, duplicated in two hooks, and its own comment flags it as a placeholder.

Evidence · useExecutiveSummary.ts:209–224 versus PUE Trend B4 and day-sheet rows 32–33.

Architecture

A reading is not attached to its equipment — only to a string prefix inside a blob

This is the answer to "is the technician inputting the right data points, attached to the specific equipment?" The data is correct. The attachment is not real.

telemetry_logs is keyed (target_hour, site_uuid, asset_id), but only two asset_id values are ever written: facility_wide and dg_daily_test. So all 324 readings for all 47 assets land in a single JSONB object per hour, and equipment identity survives only as a naming convention — ups_1_battery_voltage — with no foreign key, no per-reading timestamp, and no per-reading author.

Everything downstream inherits this. Threshold evaluation, analytics, and the Excel writer all reconstruct equipment identity by parsing key prefixes. It works, and it is why media_ambient_temp can sit on the Data Room sensor for a year without anyone noticing.

Evidence · constraint from 20260731_dg_test_separate_asset.sql; writers at useTelemetryMutation.ts:69 and useTelemetryData.ts:659,682.

Blocker

There is no aggregation in the database at all

No rollup tables, no materialised views — nine views exist and none of them aggregate telemetry. Every screen pulls raw rows and computes averages in JavaScript, and useDashboardData caps the pull at MAX_ROWS_PER_FETCH = 3000.

A year of hourly readings is 8,760 rows of fat JSONB. The monthly and yearly views you want cannot be built on this — they would silently truncate. This is the single largest blocker to the analytics expansion, and it has to be solved before any of it is drawn.

Evidence · view inventory across all migrations; useExecutiveSummary.ts:145 selects target_hour, metrics raw.

Missing

Thresholds are pass/fail — there is no amber

Limits live correctly in one place: equipment_parameters.min_value / max_value, with evaluate_thresholds() raising work items on breach and severity_from_excursion() grading how far outside. That part is sound.

But a value is either inside its band or outside it. There is no approaching the limit state, so the red / amber / green reading you want cannot be derived — and screens invent their own instead. ThermalAnalytics hard-codes humidity between 40 and 60 = Nominal and a chart axis of 15–30°C, neither of which comes from the registry.

Evidence · 20260820b_threshold_alarms.sql:30–56; ThermalAnalytics.tsx:66–69, 159, 210.

Consistency

The design tokens exist and are being bypassed 2,402 times

The rule is that colour lives in brand.css and names in branding.ts. In practice there are 2,402 raw Tailwind palette classes (bg-slate-50, text-red-500) and 70 hard-coded hex literals across 45 component files.

ThermalAnalytics is the whole problem in miniature: chart lines correctly use var(--color-danger-500), while the axis beside them is #94A3B8. This is why nothing looks unified — not taste, just two systems running at once.

Evidence · pattern count across src/features and src/shared.

Modularity

Duplication is in the logic, not in dead files

Worth saying clearly, since it shapes the cleanup: there is very little dead weight. Only three unreferenced modules exist (362 lines total — seedDatabase.ts, AuditTrailModal.tsx, ImageWithFallback.tsx), and the shadcn UI folder is almost entirely in use.

The bloat is repeated logic. avg is defined in four files, min in seven, max in four, numOrNull in two. Each analytics screen re-derives the same statistics from the same blob. Deleting files will not fix this; extracting a domain layer will.

Evidence · unreferenced-module scan across src; helper definition counts.

Coverage

Four logbook sheets are never written at all

Environment, Earthing, DG Battery Log and Inergen Gas Cylinder hold real data in the template but have no mappings and no corresponding metrics. They are weekly and monthly records — cooling status, lighting, fire detection, earth pit resistance, battery voltage — filled in on paper today.

Also worth noting: the blueprint has 27 aircons but the PAC sheet has 23 slots. The Dragor unit and all three HQ aircons have nowhere to go.

Evidence · sheet-to-mapping coverage across both workbooks; blueprint AIRCON inventory by room.

Data loss

The whole fire-safety sheet comes out blank, and it is mapped

FSS & VESDA is a daily check across six zones — gas release panel, detector LEDs, Inergen pressure, smoke detector, nozzle clearance, FAS alarm, VESDA pipe, loose connections, panel battery voltage, remarks. Sixty columns, all mapped, and not one of them has a source.

The mapping expects assets named fss_switch_room, fss_ibm_room, fss_power_room, fss_battery_room, fss_enterprise_1/2. The blueprint's only fire-suppression asset is fm200_panel, carrying one metric. Those six zone names are a further room vocabulary that appears nowhere else in the system — a fifth, after the blueprint's, the day sheet's, the Temp Record's and the Environment sheet's.

So the daily fire-safety record has been producing an empty sheet. This did not surface in the first pass because the sheet has mappings — the gap is only visible when the mapping keys are checked back against the metrics that feed them.

Evidence · 60 fss_* keys resolve to no blueprint metric and no equipment; getFssRoomOffset in excelMappingHelpers.ts names the six expected assets. Found by scripts/generate-excel-targets.mjs.

Data loss

Generator load never reaches the day sheet — and corrupts two derived sheets

Columns N–S of every day sheet are the DG Load Details block: load on DG in amps R/Y/B, and DG voltage line-to-line R/Y/B. All six are mapped to dg_load_amps_* and dg_load_voltage_*, and no equipment owns those keys. Each generator carries its own metrics; nothing carries the facility-level figure for whichever machine is currently running.

The consequence travels. Power Plant · UPS 1 computes its input voltage as ='1'!$E6+'1'!$N6 — grid amps plus DG amps — so a permanently empty column N feeds a wrong number into all four Power Plant check sheets, which then read as populated rather than as missing.

Evidence · 6 dg_load_* keys with no owning asset; formula read from Power Plant - UPS 1 row 4.

Cadence

HQ is asked for readings six times more often than anyone goes there

HQ Power Room is a separate building on its own visit cycle — every four hours. The blueprint has room_hq_ambient at hourly and its three aircons at 2-hour, the same cadence as rooms the technician passes every round.

So the form demands HQ temperature 24 times a day for a room visited 6 times, and HQ aircon readings 12 times for the same 6 visits. The unfillable rounds become blank cells that look like missed captures rather than a cadence that was never real. It also explains why hq_ambient_* has no daily-canvas column and appears only on the 4-hourly Temp Record — the sheet already knew, the registry didn't.

Correct cadence for the HQ room and all three HQ aircons is 4-hour.

Evidence · blueprint frequencies for room_id = room_hq; confirmed against Temp Record (4-hourly) versus PAC (2-hourly). Open · room_workstation and fm200_panel are also assigned to the HQ room but captured hourly, and both write to the hourly day sheet — either they are physically elsewhere or their room assignment is wrong.

05

The plan

Eight stages, in dependency order. Each is shippable on its own and leaves the system working. Stages 1–3 are foundation and contain no new features — that is deliberate, and it is what makes everything after them small instead of enormous.

Stage 1 · complete

The bar was deleting the blueprint changes nothing on screen. It is deleted. SITE_01_blueprint.json, SITE_02_blueprint.json and excelMappings.ts are gone, along with three dead modules, and the database holds all of it: 14 rooms, 47 assets, 324 readings, 10 walking steps, 572 Excel destinations — every figure matching the files they replaced, exactly.

Also landed: capture_mode so a workbook column can print NA without ever reaching a technician; facility-mode visibility as data, so generators leave the round when the site runs on mains; the HQ four-hourly correction; and 151 readings marked graphable, which TelemetryChart had been filtering on and finding none of.

Stage 2 · complete

61,774 readings now exist as rows — each attached to its asset by foreign key, to its room, and to the technician who took it. Not one is unattributed. A trigger keeps them in step with every new write, including edits that clear a field.

Fixing the model exposed two faults that had been invisible. evaluate_thresholds() could never have raised a single alarm: it joined assets on telemetry_logs.asset_id, which is 'facility_wide' on every row ever written, and rebuilt the metrics key as equipment_id || '_' || parameter_name when the parameter name is already the whole key. Behind it sat a second: resolve_recovered_thresholds() moves a job OPEN → RESOLVED, which the state machine forbids — masked because nothing had ever raised a job for it to close. Both are fixed and the cycle was tested end to end.

The blocker is now evidence, not code: 1 of 187 captured parameters has a limit configured, so red/amber/green resolves to unknown everywhere. parameter_observed_range reports what each reading has actually done so those bands can be set against the record.

Stage 3 · complete

Aggregation is in the database. readings_daily and readings_monthly store sum and count, never an average, so a month re-aggregates correctly across capture that ranges from 1 to 17 readings a day — the mean of daily means would have been quietly wrong. get_series() is the one entry point for every chart: hour, day, month or year, grouped by asset, room or site. A full year of monthly data for every parameter returns 603 rows in 345 ms, against a path that previously pulled a million raw rows and truncated at 3,000.

PUE was inflated by roughly a factor of two. The application counted UPS output alone as IT load; the workbook counts rectifier DC power as well. On the real readings that is 138.3 kW versus 275.9 kW — the rectifiers carry as much DC load as the UPSs carry AC. Corrected to the workbook's own definition.

A third dead alarm path turned up on the way: check_ingestion_health(), the job that fires when no readings are arriving at all, had been failing on every run because it inserts an incident without a ticket_number, which is NOT NULL with no default. Fixed at the column, not the caller.

Stage 4 · complete

Fifteen defects corrected in the export, against a conformance test that reads the real template headings and exits non-zero, so CI can gate on it. The audit had found four; verifying each one properly turned up eleven more.

The worst were silent. The PAC sheet aimed voltage_ry and voltage_yb at Remarks and Technician Name — roughly ten thousand cells an export overwritten with NA, destroying the columns that record who performed each check. Eight aircons sat one row low because the helper reserved a slot for a Power Room 1 unit that does not exist, so Power Room 2's readings were filed under IT Room 1. DG Check wrote battery voltage into the amps column. And both workbooks shipped dated June 2026 whatever month was exported.

Every column index and row position is now data, checked against the document it writes into. excelMappingHelpers's PAC table is gone — the row an asset occupies lives on the asset.

Stage 5 · complete

The Inventory writes. Rooms, equipment with room and cadence, readings with unit and capture mode, and a four-value band — hard minimum, amber low, amber high, hard maximum — with what the reading has actually recorded shown beside it as evidence rather than as a suggestion. Both creation buttons said "disabled (defined in config blueprint)"; that blueprint was deleted in Stage 1, and rooms had carried admin write policies the whole time.

Nameplate facts needed no new machinery. A generator's burn rate is a parameter with capture_mode = CONSTANT and semantic_role = FUEL_BURN_RATE — same table, same editor, no special case. A dedicated column written earlier in this stage was dropped again in favour of it: two ways to express one kind of fact is how the drift began.

The role is the answer to how does a calculation find a reading an administrator typed. It asks for the role, never the name — the string-matching that produced media_ambient_temp, asset_id = 'facility_wide' and a rebuilt metrics key. 36 parameters tagged, one role per asset enforced.

Also closed: four views were reading past row-level security, so a technician could ask PostgREST for another site's jobs. Six others still do, reported rather than changed — each needs its callers checked the same way.

Execution rule · agreed

Right and done, over quick and undone. The foundation is not compressed to hit a demo date; if the work runs past next week, more time gets asked for.

Within that, each foundation stage is built vertically first: Temperature & Humidity, per room, is carried all the way through registry → readings → rollups → status → detail view → Excel before the remaining categories follow. The pilot proves the pattern under real load and the rest become mechanical repeats rather than fresh invention. It also means there is a working, demonstrable product at every point after stage 3 — not as a compromise, but because a vertical slice is the honest way to find out whether a foundation actually holds.

01

Collapse three definitions into one

Nothing renders from the blueprint JSON or the TypeScript mapping file. equipment_parameters becomes the only place any of it is written down.

  • Populate excel_workbook, excel_sheet_name, excel_column_index from the TS mapping as a one-time migration — the columns already exist.
  • Add excel_row_rule so cadence and block geometry are data, not a switch in the writer.
  • Retire excelMappings.ts and excelMappingHelpers.ts; the export engine reads the registry.
  • Migrate the seven runtime consumers of the blueprint JSON onto the registry. The file becomes a versioned seed input, not a runtime dependency.
  • Rename media_ambient_* to data_ambient_* with an alias column, so the legacy key keeps resolving.
  • Correct the HQ cadence: room_hq_ambient and the three HQ aircons move to 4-hour. Resolve whether room_workstation and fm200_panel really live in HQ.
  • Add capture_mode — CAPTURED / CONSTANT / NOT_APPLICABLE. See below; this is the mechanism that absorbs both the 291 orphans and the four unwritten sheets.
  • Delete the three unreferenced modules.

Done when · deleting SITE_01_blueprint.json at runtime changes nothing on screen.

1b

One mechanism for "not collected yet"

Everything the workbook asks for exists in the registry, whether or not a person is currently typing it — and turning one on later is an UPDATE, never a deploy.

is_constant and constant_value already exist, and constants already flow into the saved payload and out to Excel. The only gap is that a constant renders as a read-only field rather than disappearing. capture_mode closes it:

capture_modeTechnician seesExcel receivesUsed for
CAPTUREDAn input fieldThe readingThe 323 metrics collected today
CONSTANTRead-only nameplateconstant_valueUPS KVA, bank capacity, model
NOT_APPLICABLEnothing at allNAThe 291 orphans; the four static sheets
  • Register all 291 orphan mappings as real parameters at NOT_APPLICABLE, defaulting to NA — chiefly per-aircon voltage and current. The logbook columns fill with NA instead of blank, and the technician never sees them.
  • Register Environment, Earthing, DG Battery and Inergen the same way — as assets with weekly and monthly parameters, seeded from the template's current values. No separate static store, no new tables. An earth pit is an asset; earth resistance is a monthly parameter with a limit.
  • That last point is what makes the earthing data useful rather than merely stored: "which pits are acting up" is a trend against a threshold, which the readings spine gives for free — a static record cannot answer it.

Done when · switching a parameter from NOT_APPLICABLE to CAPTURED makes the field appear on the phone and the real value appear in Excel, with no code change.

02

Give every reading a real home

A reading belongs to an asset, a parameter, an hour and a person — by foreign key, not by string prefix.

  • New readings table: (site, asset_id, parameter_name, target_hour, value_num, value_text, technician_id, shift_session_id, entered_at), keyed on the first four.
  • Backfill by exploding the existing JSONB through the registry's metric_prefix, so no history is lost.
  • telemetry_logs stays as the write path initially and a trigger fans out into readings — no big-bang cutover, both readable throughout.
  • Room becomes a dimension, not a label. Every reading carries its room, because averaging rooms that sit in different buildings is the flaw this platform exists to correct.
  • Add the amber band: warn_min / warn_max alongside the existing hard limits, and one reading_status() function returning green / amber / red. Every screen calls that and nothing computes its own.
  • Stamp the limit values onto each breach when it is raised, so widening a band tomorrow cannot rewrite last month's breach count.

Done when · "show me every temperature Chanda recorded in Power Room 1 last Tuesday" is one query.

03

Aggregate in the database

The browser never computes a statistic again, and the 3,000-row ceiling disappears.

  • readings_hourly → readings_daily → readings_monthly rollups, each carrying avg / min / max / count / breach-count per asset-parameter and per room, with the site figure as a roll-up of rooms rather than a flat average across them.
  • One RPC — get_series(asset, parameter, from, to, grain) — where grain is hour, day, month or year. Every chart and every table on the platform is a call to it.
  • Refresh on the existing scheduled-job spine, incrementally.
  • Move avg, min, max, numOrNull out of the fifteen files that define them into one domain module — then delete the copies.
  • Correct PUE to the workbook's definition and lift DG_BURN_RATE_LPH into per-generator registry data.

Done when · a full-year monthly view loads from one request and matches the workbook to the decimal.

04

Fix and prove the Excel mapping

The export is correct, and stays correct because a test says so rather than because someone checked once.

  • Fix the four confirmed defects: Temp Record's four-column shift, the PAC row expression, the DG off-by-one, and fullCalcOnLoad.
  • Verify the DG Check block size, which I did not confirm — its 6-row-per-day assumption is untested.
  • Build a conformance test that reads each template, walks the registry, and asserts that every destination cell sits under the heading it claims. Run it in CI. This is the piece that prevents a repeat.
  • Month selection. Under a month of history, export everything; past that, pick the month. The list offers only months that actually hold readings.
  • Write the dates. Every date cell has a known address — day sheets BV1, DG sheets A4:A34, Temp Record every sixth row from A7, PAC once per block. The template ships hardcoded to June 2026; the export stamps the selected month. Bounded, mechanical, and it removes a manual step that is itself a defect source.
  • The template in public/ is never mutated — each export loads a fresh copy in memory. That already holds, so "copies that don't get reused" needs no new machinery.
  • Generated workbooks are not stored. They are regenerated from the readings, which are the one source of truth; a stored binary diverges the moment a reading is corrected. The exception: when an admin signs a month off, that immutable copy is archived with the signature as the compliance artefact.
  • The 291 orphans need no decision here — stage 1b registers them as NOT_APPLICABLE, so their columns carry NA.
  • PAC stays at 23 rows so the delivered logbook matches what the client already reads. The Dragor and the three HQ aircons are captured, trended and alarmed inside DCIMe, and appear in its analytics and print views.

Done when · picking August produces two workbooks, dated August, with every sheet populated and every column under its own heading.

05

Admin control plane

Bands, parameters, equipment and room assignment are all editable by an administrator, because none of them are fixed facts.

  • Amber band editing — extends ParameterLimits, which already writes hard min/max, to the new warn bounds.
  • Equipment lifecycle: create a unit, choose its template, name its model and manufacturer, assign it to a room, set its cadence. AssetInventory can only toggle is_active today, so this is genuinely new.
  • Parameter editing on an instance: label, unit, cadence, limits, and the capture_mode switch that turns an NA column into a live field.
  • Every change audit-logged with who and when — these edits move what the platform alarms on.

Done when · adding an inverter to Power Room 1 with its own parameters is a screen, not a migration.

06

Unify the visual layer

One palette, one status vocabulary, one set of primitives — so a new analytics page is composition, not invention.

  • Codemod the 2,402 raw palette classes and 70 hex literals onto tokens.
  • Green / amber / red become semantic tokens driven by reading_status(), never chosen per component.
  • Extract the primitives every detail view will need: MetricTile, StatusPill, TrendChart, StatTable, PeriodPicker, PrintFrame.
  • Split the four largest components — IncidentReport (1,610 lines), NocOverview (1,225), RoutineTasksDashboard (1,047), AssetInventory (1,036) — into view plus hook plus presenter.

Done when · a new category detail page is roughly 150 lines because everything it needs already exists.

07

Build the detail views

Executive summary stays the glance. Behind every tile sits a full instrument: raw readings, interpretation, trend, and narrative.

One page per category — Temperature & Humidity, Utility, Generator & Fuel, UPS, Rectifier, Aircon — each built from the same four bands:

  • Now — current value per room or asset, status colour, and the trailing two hours, since that is what says whether a number is drifting or settled.
  • Raw — every hourly reading with the technician's name against it, filterable by hour, day, month, year or a custom range. This is the register the day sheet is.
  • Interpreted — avg / max / min for the selected period, breach counts, time spent outside band, and the same figures for the period before it.
  • Narrative — generated prose stating what crossed which limit, when, for how long, and who was on shift. Written from the rollups, so it cannot disagree with the chart above it.

Every page carries a print frame producing the same content as a signed A4 document, reusing the signature machinery already built for report sign-off.

Done when · every figure on the executive summary is one click from the hourly readings and the person who took them.

08

People, vendors and incidents

The same treatment applied to the human side of operations.

  • Technician analytics — readings logged versus expected, capture punctuality, jobs assigned versus acknowledged versus completed, acknowledgement latency, incidents raised and resolved, shift coverage.
  • Vendor analytics — extends the existing vendor_activity view: response against SLA, visits, findings by severity, open work, flag history.
  • Incident analytics — who responded first, first-level troubleshooting outcome, escalation path, time to acknowledge and to resolve, recurrence by asset.

Done when · "how did we perform last month, and who did what" is a page rather than a conversation.
